  every 5–15 min), writes results to a small DB/JSON file.
  - The site/API just reads that cached data instantly — no Chromium in the
  request path, no cold-start roulette, no "slow."
  - Same pattern covers PDF generation reasonably well too (pre-render common
  reports on a schedule), though one-off PDF requests can still hit the
  microservice live since that's an explicit user action, not a passive page
  visit.

  1. Oracle Cloud "Always Free" VM — a real, permanently-free micro VM (no

● Here's how it maps onto your actual code (I read daily-report-data,
  monthly-report-data, metlife-report, and lib/monthly-data-cache.ts to check).

  What GitHub Actions is

  It's an automation runner built into every GitHub repo. You commit a YAML file
  to .github/workflows/, and GitHub spins up a temporary Linux VM (free, no
  noexec/sandbox restrictions like cPanel) to run whatever commands you give it,
  on a trigger — a push, a manual button click, or a cron schedule. It's a
  completely separate machine from wherever your Next.js app is hosted.

  Why this fixes your actual bug

  I found it — lib/monthly-data-cache.ts writes its cache to os.tmpdir(). On
  Netlify/Vercel, /tmp is per-instance and ephemeral: every time a new
  serverless instance spins up (cold start), it has an empty /tmp, so it must
  scrape live — which is slow and sometimes doesn't finish in time. Once that
  instance is warm and its /tmp has data, requests routed back to it look
  "fast." That's exactly the "no data first few refreshes, fine afterward, slow"
  pattern you described. daily-report-data and metlife-report don't even have
  this fallback cache, so they always scrape live.

  The plan

  1. A workflow file runs on a schedule (e.g. every 10 min):
  .github/workflows/scrape.yml with on: schedule: - cron: "*/10 * * * *" (plus
  workflow_dispatch so you can also trigger it manually from GitHub's UI).
  2. It checks out your repo, runs npm ci, then a small script
  (scripts/scrape.ts) that reuses your existing login/scrape logic from the
  three routes — but using plain puppeteer (bundled Chromium), since GitHub's
  runner has no restriction on executing binaries, unlike cPanel.
  3. Instead of returning JSON to a browser, the script writes the result to a
  shared, durable store — since the GitHub runner is a different machine than
  your web host, it can't write to a local file your app can see. This needs a
  small free hosted store, e.g. Upstash Redis (simplest — free tier, just a URL
  + token, perfect for "latest snapshot" data like this).
  4. Your three API routes change from "launch browser, scrape, return" to "read
  latest snapshot from Upstash, return" — instant, no Puppeteer in the request
  path, no cold start, works identically on cPanel, Netlify, or Vercel.

  What you need to do to set it up

  1. Create a free Upstash account (upstash.com) → create a Redis database →
  copy the REST URL + token.
  2. In your GitHub repo: Settings → Secrets and variables → Actions, add
  secrets: ADNSMS_EMAIL, ADNSMS_PASSWORD, METLIFE_EMAIL, METLIFE_PASSWORD,
  UPSTASH_REDIS_REST_URL, UPSTASH_REDIS_REST_TOKEN.
  3. I write the workflow YAML + scrape script + update the three routes to read
  from Upstash instead of scraping live.
  4. You test it via the "Run workflow" button in GitHub's Actions tab before
  trusting the schedule.

  Everything stays free (GitHub Actions: 2,000 free min/month on a private repo,
  this job takes seconds; Upstash: generous free tier, no card required). PDF
  generation stays separate — that's user-triggered, not passive, so a Vercel
  serverless function with your existing Puppeteer code is fine for that.
